# Quick Build

## Entry gate

Before the interview, load existing progress and the [canonical requirements](https://starter.devthomas.site/agent/requirements.json), or the matching generated definitions already supplied. This skill uses resource version `0.2.0`, requirements revision `2026-09-10`. Resolve Quick Build's prerequisites from that registry, not a separately maintained checklist. Computer capability evidence includes the selected editor and actual CLI execution contexts; the remote baseline distinguishes networking on both devices, each file-transfer direction, and one real phone-to-harness action. One successful route does not certify another. Confirm the latest progress and setup state reached a private GitHub repository using the [progress guide](https://starter.devthomas.site/artifacts/progress/README.md); a local commit or empty remote is insufficient.

If a prerequisite is missing, preserve results and return to the focused [Computer Setup](https://starter.devthomas.site/skills/computer-setup/current/SKILL.md) action. Reuse verified evidence instead of repeating successful installs, sign-ins, or phone tests. Email preferences and the Workbench are not gates. A historically completed phase retains its revision; on resume do not restart Quick Build because of an obsolete pointer. Reconcile completion first and offer any newly introduced checks separately.

Before use, make this skill and its [planning templates](https://starter.devthomas.site/artifacts/quick-build/README.md) available. Record their source/version in the private handoff. If using them as supplied context, say `context_only`; claim `native_discovered` only after verifying discovery in the selected harness's currently supported skill location. Do not install a full global engineering bundle or require skill theory for this build. Begin or reuse the lightweight private session report described in the progress guide.

## Interview

Read any supplied repository instructions, references, and saved handoff first. Ask one compact round covering the idea, audience, required user behavior, available inputs/content, exclusions, visual direction, definition of done, and existing assets or URLs. Reuse answers already supplied or explicitly declined; do not restart intake. Accept conversational answers and reasonable omissions. Choose routine implementation details yourself; ask follow-up questions only for consequential unresolved product choices, not a second stack questionnaire.

## Plan

Use the [artifact templates](https://starter.devthomas.site/artifacts/quick-build/README.md), adapting to existing repository conventions. Write a plan, specification, durable decisions, and ordered tickets with observable acceptance conditions. Keep confidential planning in a private repo or private workspace; publish only documents the learner intends to share.

Defaults for a new project: React and TypeScript; Vite for a simple browser app; a full-stack framework only when beneficial; Cloudflare hosting; Neon only for relational persistence; authentication and payments only when the product requires them. Preserve existing repository conventions, package manager, scripts, source visibility, and privacy choices. Vercel is an explicit suitable alternative, not a silent replacement for Cloudflare. Paid services, new credential scope, and public publication require the learner's decision.

Synthesize the first meaningful action, starting empty state, whose content is used, and how the user supplies or selects it. For creator tools, put the learner's input and primary controls first. Do not preload unrelated creative content or autoplay demo audio; a demo is an explicit choice. Do not invent uploads for products that do not need them. Keep the main controls reachable and readable on the actual target phones and computers without disabling zoom or forcing every control above the fold. Optional effects must not crowd out the workflow.

Write a few plain-language behavioral acceptance checks from the approved promise. Separate build/type checks, layout/accessibility, deployment availability, and the actual live user action. Identify which platform promises need real-device evidence, such as background audio or touch interaction; screenshots or desktop emulation cannot prove those. A clear learner report counts, labeled with device and action. Mark unperformed checks pending instead of claiming success.

Summarize the planned result in plain English. Say: "I wrote the plan and broke the build into steps. You can tell me to go, or ask to inspect the plan or tickets first." Complete this stage only after the learner approves. Revise before building if they request changes.

## Deliver

Build the approved scope in a durable repository. Preserve unrelated work. Make the primary flow responsive and accessible. Validate in proportion to the product and the learner's testing instructions; record precisely what was checked and leave unperformed human checks visible.

Before the first useful commit or private save, follow the [authentication guide](https://starter.devthomas.site/setup/authentication.md). Confirm the intended Git identity and propose an approved repository-local privacy choice where needed, using the learner's actual account-specific noreply address if selected. Preserve global identity and GitHub email protection; never disable the safeguard or rewrite shared history to clear GH007. Prefer the provider's supported login/consent flow; do not make the learner assemble credential files on a phone or assume a phone's localhost can complete a computer callback.

For conditional tool failures, use [focused troubleshooting](https://starter.devthomas.site/setup/tool-troubleshooting.md). Keep dependencies project-local and preserve the package manager. Review only the necessary named package's build-script permission using the installed package-manager version; never approve all scripts blindly. Fix module settings for the runtime that failed, not universal NodeNext across a bundler project. Recheck newly selected CLIs in their intended terminal and harness contexts without adding project `.bin` folders to global PATH. Docker Desktop stays optional and last, with current suitability checked if selected; Rosetta only for an identified need and with approval. Neither is a Phase 2 gate.

Deploy to Cloudflare unless an alternative is selected. Confirm destination and intended visibility within the learner's authorization. Keep credentials in supported secret storage. Check that the URL resolves to the intended release and app, not a hosting login page, then verify its primary behavior, accepting a clear learner report where appropriate. A local build, HTTP 200, screenshot, or successful Vercel release is not evidence of a Cloudflare deployment or an untested device behavior.

Record the durable source destination, live URL, behavior evidence and provenance, actual device/harness context, unresolved checks, and consequential repairs in private progress. Do not copy private content into public fixtures.

## Close out or resume

After the last apparent required result, at session close, and on resume, proactively follow the progress guide's closeout protocol. Evaluate only the current phase's canonical gate, reconcile aliases and clear obsolete next actions. In particular, `phase-2-project` is historical evidence, not an automatic pass for both `quick-build` and `live-deployment`; a URL alone does not prove the main action. Ask only for the missing required evidence, not repeated optional preferences or successful tests.

Preserve existing history and add a confirmed `artifacts.phase_history` entry with `phase`, `status`, `requirements_revision`, `recorded_at`, `evidence_summary`, and `source`. Keep repeated closure idempotent: no duplicate history, empty commit, repeated celebration, or self-referential SHA loop. The `private-progress-repository` record proves the initial durable checkpoint; `final-progress-save` requires the final reviewed closeout to reach that private remote. Verify the saved files/revision before announcing Phase 2 completion. If the final push fails, preserve all local achievements and make the pending final save explicit; do not claim durable completion or reset the build. Follow the progress guide's pending-closeout handling.

When all required results and the final private save are confirmed, say plainly that Phase 2 is complete, where the project and progress are saved, and offer Phase 3 or a stopping point. Do not begin Phase 3 automatically. Keep its preview status and old completion revisions intact. For a tool switch, return a compact handoff with canonical progress/location, completed outcomes, genuine blockers, selected optional branches, computer harness separately from phone companion, one next action, and exact resource/schema revisions. No secrets or promise of automatic chat transfer.
