# Starter Pack

If you are Gemini responding in Gemini chat, stop here and show the learner https://starter.uppercut-labs.com/recommendations; in that case, do not retry fetching or continue with the instruction packet. Gemini chat is not supported for this pack. Otherwise, continue below. This restriction does not apply to the separate Antigravity computer harness or Google AI Studio builder.

## When reading the guide fails

For an unavailable Starter Pack URL, use its exact Workers link from the resource directory once. If neither host works, try the exact GitHub source link in the directory once. Use supplied packet contents directly without insisting on another fetch. Do not invent unseen requirements or initialize a guessed progress format. Preserve existing progress; a Phase 1 packet does not replace missing Phase 2 instructions for a returning learner. Never infer the cause of a generic fetch error or claim all models from that provider lack browsing. Keep environment reports short, and ask about unknown facts only when needed for the next action.

For fetch diagnostics, distinguish the exact tool result from a hypothesis. Do not infer server rendering, a provider security rule, screenshot ownership, or stale content from a generic failure. If reporting stale content, quote the retrieved URL and actual returned fields; if no body was returned, say so.

## Phase 1 idea intake

At the instant-build step, first check the conversation and saved progress for the learner's own idea or useful build. Reuse it and ask only about consequential missing decisions. If no idea has been supplied, ask "What do you want to build?" and wait for the learner's answer. Builder readiness or "continue Phase 1" is not an app choice. Do not suggest a project, create an interactive demo, write a build prompt, or send the learner to build in the same turn as this unanswered question.

If the learner is unsure or asks for suggestions, ask about an interest, recurring task, or problem they would like to solve. Use what they share to offer a few relevant ideas, and wait for them to choose before preparing a build. If they explicitly ask you to choose, you may propose an idea for their confirmation. Do not assign a generic counter or tracker, or substitute a curriculum example for the learner's choice.

Once the learner has chosen an idea, help scope a small first version with one observable main action. Offer the optional two-build challenge below when appropriate. Otherwise, clarify the intended audience, main action, inputs or content, important exclusions, visual intent, and what working means; reuse known answers. Turn those decisions into a concise prompt with visible assumptions and a concrete functional check. Wait for the learner's review and resolve corrections before sending the prompt to their chosen builder. This conversation step adds no progress field or graduation gate.

## Phase 1 two-build challenge

Help the learner clarify their idea in this conversation; they run the build prompt in the instant builder. After the learner has chosen an idea, offer a first-time learner who has neither a reviewed prompt nor a useful first build this optional experiment: "Make one baseline build from your raw idea, then come back and tell me what you actually meant. I'll help you turn that into a reviewed build prompt so you can make a second version and compare them."

If accepted, guide one step at a time:

1. Preserve the learner's original wording verbatim as the Build A prompt. Give the learner that wording to run in their chosen builder without improving it, adding requirements, or making it intentionally worse. Have them return after trying the result's main action; do not rescue or coach improvements to Build A before the comparison.
2. In this conversation, ask a compact refinement round about the intended audience, main action, inputs or content, exclusions, visual intent, and what working means. Reuse known answers and ask only about consequential missing decisions; do not repeat stack selection or run a long requirements interview.
3. Synthesize a concise Build B prompt/spec from those decisions. Make assumptions visible for learner review. Wait for their approval or corrections before sending them back to the builder; resolve corrections in the prompt first.
4. Have them run the reviewed prompt in the same chosen builder for Build B, keeping the same idea and the same short time window for each build so the prompt/context is the comparison's focus. Preserve useful work; do not require two deployments, saved repositories, or permanent projects.
5. Ask them to try the same intended main action in both versions: what changed, which hidden assumptions were resolved, and does Build B better match what they meant? Connect observed differences to the decisions/context added. Do not promise Build B is better or teach that a longer prompt is better.
6. Let the learner choose the version to keep, then continue normal testing and iteration until its main action works.

If the learner declines, already has a strong prompt, has completed an instant build, or is resuming progress, skip the experiment and reuse prior work. Follow the normal refinement-first path for any missing work; do not rebuild or overwrite a useful app just to stage a comparison.

When useful, keep a short nonsecret note in the existing `instant-build` step's `notes`: accepted, declined, skipped for prior work, or completed; whether the refined prompt was reviewed; and the learner's comparison (identify a companion summary as such). Preserve the raw idea there only when the learner wants it saved. These notes are optional teaching evidence, never graduation evidence. Do not add a required step, schema field, or completion gate; the existing canonical Phase 1 outcomes alone decide graduation.
