# Windows: fastwin

fastwin is a Rust template: raw Win32, a D3D11 flip-model swap chain, and Direct2D/DirectWrite for custom drawing. It provides pacing, DPI, primitive input, text caching, virtualized lists, idle trimming and `--bench`; these do not establish complete controls or editing. An app implements one `App` trait and draws its frame. Its [README](../starters/README.md) is the API reference. Read it and the capability limits below before writing code.

## Steps

1. **Get the template for a new app.** Copy this skill's `starters` folder to a scratch folder, or take it from a fresh checkout of the repository that holds this skill, and record the revision. Its [README](../starters/README.md) covers the files. Done when `fastwin\Cargo.toml` and `new-app.ps1` exist. For an existing app, inspect and build its current project instead; preserve its data and build configuration.
2. **Establish the baseline.** For a new app, run `new-app.ps1 -Name <app> -Dest <project folder> -FrameworkPath <template>\fastwin` with quoted paths. The script creates a mutable path dependency: for retained source, vendor the exact fastwin snapshot or use a pinned Git revision, retain `Cargo.lock` and record provenance/upgrade policy. Follow workspace folder rules. Done when `cargo build --release` succeeds and retained source rebuilds without the scratch checkout. For an existing app, record its baseline build result before edits.
3. **Build one working action**, then expand to the requested behavior. Implement `App` through the primitives in the README: `event` requests redraw for visible changes, `update(dt)` advances motion, and `bench_step` exercises the app's real workload. Lists use `List`; text uses `Canvas::text`. Done when the requested behavior works with representative data, the release build succeeds, and the language-guide review has no findings.
4. **Verify.** Follow [verification](verification.md). Run `<app>.exe --bench` on an authorized display and retain the fresh `bench.txt`. Inspect the UI with `--no-focus`, capture it when available, then post `WM_CLOSE`. No-focus mode gets no keyboard input: reuse authorization for input-capable interactive checks, or leave keyboard behavior unverified. Done when behavior, pacing, idle and focus each have evidence and a verdict.
5. **Deliver, then tidy.** Copy the release exe, required runtime data and evidence outside `target\` before deleting build directories and temporary checkouts you created. Retain the framework dependency if the project still needs its path. Done when the handed-over exe and data still exist and their paths, tested workload, results and remaining limits are recorded.

## Refresh rate

The target remains the fastest connected display's rate. The current template uses the window display's vblank on a slower screen. A CRT-local benchmark can therefore pass that screen's baseline while the fastest-rate requirement is unmet. Report both verdicts; a local pass never becomes a full pass. An experimental branch is not evidence that this checkout implements a fix: inspect its pacing and verify it before changing the verdict.

The benchmark times render-loop intervals and elapsed wall time around workload/update/draw/`Present`, including waits inside those calls. Its `render cpu ms` label does not measure thread CPU consumption. Its `focus: never taken` line is a fixed label, not a foreground-window observation. Use the shared verification contract for evidence.

The current swap chain uses fixed-vsync `Present(1, 0)` without tearing flags. Treat VRR/G-Sync operation as unverified without capability, configuration and independent observation evidence. Keep the safe fixed-vsync path unless the product needs a tested alternative.

## Capability and reliability boundaries

- **Controls and text.** The inspected custom widgets lack an implemented UI Automation provider. Use standard native controls/dialogs or maintain names, roles, states, patterns, focus/selection events and virtualized-item access. Qualify with a UIA tree plus Narrator/keyboard tasks. `Canvas::text` draws glyphs; `Event::Char` and append/pop logic are not general editing. Prefer a narrow native edit-control bridge for fields; verify composition/cancel, caret, selection, clipboard, Unicode and DPI. Missing explicit IME handlers alone does not prove every composition path fails.
- **Persistence exemplar.** Triage's `close` currently returns true after `save()` even when `write_atomic` fails. Before reusing that flow, return/propagate save success and keep the window, dirty state and error on failure. In no-focus mode `Ctx::ask` answers No without a dialog; use disposable data and an isolated input-capable session to test actual Save/Discard/Cancel. Reverse choice cycling is triage-specific, not general undo; real undo restores previous values by stable ID.
- **GPU and host lifetime.** Inspect resize/target creation/`Present` error propagation and all early exits before relying on recovery. The current host installs a global pointer before failure-prone initialization and clears it on normal exits only. Keep single-host/thread entry guarded, destroy owned HWNDs before releasing their state and reset pointers on every exit. Inject call-level initialization/resize/present failures in an isolated fixture; recovery must be bounded or end in an actionable terminal error. General multiwindow support is separate scope.
- **Search and memory.** Preserve visible-row virtualization and blocking idle. Measure search fields, filter/sort latency and resume tails separately from scrolling. The four-second working-set trim has an unmeasured tradeoff: compare trim on/off, residency, private commit, faults and first-response latency before changing it or claiming lower energy.
- **Output and handoff.** Current bench/log files are installation siblings and benchmark write failure is ignored. Use a known writable per-user location or explicit output path in the app being delivered; surface write failure and keep a fresh run identity. Retain required runtime data outside build folders. A compiled exe does not need the fastwin source at runtime; rebuildable source does need its pinned dependency. Choose portable/local versus installer/public release explicitly.

These are source-observed template limits, not reproduced runtime incidents or fixes already supplied by the template. Recheck them at the recorded checkout revision; apply only the corrections needed for the app's capabilities and claims.

## Launch rule

Every agent launch on the owner's active session uses `--bench` or `--no-focus`. In a dedicated authorized interactive session, clear `FASTWIN_NO_FOCUS` for that test process and launch without either flag to exercise keyboard, dialogs and assistive input. Record the isolated session identity; ordinary background-display authorization does not authorize this mode. Where the development layout exists (a 4:3 CRT beside a 4K panel), keep the **CRT** default and **4K** aliases; `--display 4k` uses the main screen and needs existing authorization for that check. Otherwise use the owner-decision workflow in `SKILL.md` before placing a test window where the owner is working. These resolution heuristics describe one machine's layout, not generic monitor identities: record actual current output, scale, orientation and rate, and verify placement on other topologies. The current template has not yet gained a generic stable-display selector.

## Framework changes

Changing `fastwin` itself (pacing, swap chain, display selection) needs a bench of `hello` and `triage` from the template covering each distinct edge case once: the CRT, a cold first launch, and a display change mid-run if pacing changed. Every case must reach the target with 0 hitches. Report the 4K as unverified unless the owner allowed a 4K bench.
